# وثائقي — نظام إدارة الوثائق

نظام عربي احترافي لإدارة الوثائق الرسمية: مكتبة وثائق، رفع ملفات Word وPDF والصور، معاينة داخل المتصفح، طباعة مرنة، قوالب وترقيم وترويسة، وصلاحيات وسجل تدقيق. يعمل بواجهة React وخدمة API مبنية على Appwrite.

## المزايا الحالية

- **مكتبة الوثائق:** عرض الوثائق في بطاقات، بحث، تصنيفات، إحصاءات، ومعاينة سريعة، مع إنشاء الوثائق وتحرير المسودات وإصدارها وأرشفتها وإدارة القوالب.
- **رفع الملفات:** سحب وإفلات أو اختيار ملفات `Word` (docx) و`PDF` والصور، مع التحقق من النوع والحجم (حتى 25 ميجابايت) وعدّ الصفحات تلقائياً.
- **المعاينة:** عرض PDF عبر `pdfjs`، وWord عبر `docx-preview`، والصور مباشرة، دون مغادرة النظام.
- **الطباعة الذكية:** طباعة صفحة واحدة في الورقة، أو صفحتين، أو 4 صفحات في ورقة A4، مع هوامش قابلة للضبط وترويسة وتذييل وترقيم وعلامة مائية.
- **إعدادات المؤسسة:** ترويسة الوثيقة، الشعار، ألوان الفاصل، الترقيم الصادر والوارد، ورمز التحقق QR.
- **الإدارة:** المستخدمون والجهات والصلاحيات وسجل الإجراءات والتدقيق.

## البنية التقنية

- **الواجهة:** React 19 وTypeScript وVite وTailwind CSS، مع دعم RTL وخطوط عربية.
- **API:** tRPC مستضاف في Appwrite Function باسم `wathaeqi-api`، مع مسار رفع خام `POST /api/documents/upload`.
- **المصادقة:** Appwrite Auth، مع جلسة HttpOnly موقعة من الخادم.
- **قاعدة البيانات:** Appwrite TablesDB ضمن قاعدة `wathaeqi-db`.
- **الملفات:** Appwrite Storage عبر موفر التخزين الخادمي، بمفاتيح آمنة تحت `documents/{userId}/`.
- **معاينة الملفات:** `pdfjs-dist` لـPDF، و`docx-preview` لـWord، و`html-to-image` لتحويل الصفحات إلى صور عند الطباعة والتنزيل.

## إعداد البيئة المحلية

المتطلبات:

- Node.js 24 أو أحدث.
- pnpm 12.14.0.
- مشروع Appwrite مع Auth وTablesDB وStorage وFunction مهيأة.

ابدأ من جذر المستودع:

```bash
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env
```

اضبط المتغيرات التالية في بيئة الخادم المحلية فقط:

| المتغير                | الغرض                                                     |
| ---------------------- | --------------------------------------------------------- |
| `APPWRITE_ENDPOINT`    | عنوان Appwrite وينتهي بـ `/v1`                            |
| `APPWRITE_PROJECT_ID`  | معرّف مشروع Appwrite                                      |
| `APPWRITE_DATABASE_ID` | معرّف قاعدة TablesDB                                      |
| `APPWRITE_BUCKET_ID`   | معرّف حاوية الملفات عند استخدام التخزين                   |
| `APPWRITE_API_KEY`     | مفتاح خادمي بصلاحيات محدودة؛ لا يُرسل إلى المتصفح         |
| `AUTH_SESSION_SECRET`  | سر تشفير والتحقق من الجلسات، 32 محرفاً عشوائياً على الأقل |
| `OWNER_SETUP_SECRET`   | رمز إعداد المالك لمرة واحدة، 32 محرفاً على الأقل          |

يحتاج عميل الواجهة إلى:

- `VITE_APPWRITE_API_URL`: عنوان Function العام، وليس سراً.
- `VITE_APPWRITE_PROJECT_ID` و`VITE_APPWRITE_ENDPOINT` فقط إذا كانت واجهة العميل تستخدمهما مباشرة.

لا تضع مفاتيح API أو أسرار الجلسة أو رمز إعداد المالك في متغير يبدأ بـ `VITE_`. لا ترفع ملف `.env` إلى Git.

تُرسل جلسة الدخول كترويسة `Authorization: Bearer`، ويُحفظ رمز جلسة مشفّر ومتحقق من سلامته في `sessionStorage` بعمر أقصى 12 ساعة؛ لا يعتمد النظام على ملفات تعريف الارتباط. لا يكشف الرمز سر جلسة Appwrite، لكن يمكن لثغرة XSS سرقته وإعادة استخدامه قبل انتهاء صلاحيته؛ لذلك يجب إبقاء أسرار الخادم خارج الواجهة ومعالجة ثغرات XSS فوراً.

في Appwrite Function تُستخدم هوية التنفيذ ومفتاحها قصير العمر عند توفرهما؛ لا تنسخ مفتاحاً خادمياً إلى ملفات الواجهة. يجب أن تحتوي `APPWRITE_WEB_ORIGINS` على أصول الويب المسموح بها حرفياً، مفصولة بفواصل.

## تشغيل وبناء المشروع

```bash
pnpm dev
```

فحوص الجودة:

```bash
pnpm lint
pnpm check
pnpm check:responsive-shell
pnpm test
pnpm build:appwrite-api
pnpm build
```

بناء حزمة Appwrite API يتحقق أيضاً من عدم تضمين استيراد SDK الخاص بـSupabase. لا تعتبر نجاح البناء وحده إثباتاً لعمل تسجيل الدخول أو الجلسات أو رفع الملفات على الخدمة الحية.

## اختبار Appwrite

يجب اختبار هذه المسارات على بيئة معاينة معزولة، وليس عبر الكتابة التجريبية في بيانات الإنتاج:

1. فتح الواجهة من نطاق المعاينة المصرح به في Appwrite.
2. التأكد من نجاح طلب `auth.ownerSetupStatus` وظهور حالة الإعداد قبل إدخال رمز المالك.
3. اختبار تسجيل الدخول بحساب المالك الحالي، دون إنشاء حساب بديل.
4. اختبار إنشاء قالب وتعديله وتعطيله، والتحقق من حفظه.
5. اختبار إنشاء وثيقة كمسودة وتعديلها وإصدارها وأرشفتها.
6. اختبار رفع ملف Word وPDF وصورة، والتأكد من ظهورها في المكتبة وفتح معاينتها.
7. اختبار الطباعة بخيارات 1 و2 و4 صفحات في الورقة، مع الهوامش والترويسة والتذييل والترقيم.
8. اختبار عزل الملكية ومنع قراءة وثائق أو ملفات أو قوالب مالك آخر.
9. اختبار تعارض التحديث والترقيم المتزامن، والتأكد من عدم تكرار الأرقام.
10. اختبار تسجيل الخروج وانتهاء الجلسة وتغيير كلمة المرور.

معاينات Appwrite الخاصة قد تتطلب تسجيل الدخول إلى حساب عضو في المؤسسة المالكة للمشروع والتصريح لتطبيق **Appwrite Preview**. فشل فتح رابط المعاينة بسبب بوابة تسجيل الدخول لا يثبت فشل API ولا يثبت نجاح الواجهة.

## قواعد البيانات والبيانات

تستخدم مستودعات التطبيق جداول Appwrite مثل `users` و`organizations` و`organization_memberships` و`documents` و`templates` و`department_settings` و`platform_document_settings` و`app_records`، إضافة إلى جداول التدقيق عند تفعيلها. راجع `docs/migrations/APPWRITE_SCHEMA_COMPATIBILITY_AUDIT_AR.md` لمراجعة التوافق والحدود.

- لا تحذف سجلات أو ملفات Appwrite الموجودة.
- احتفظ بحساب المالك الحالي ومعرّف Appwrite Auth المرتبط به.
- لا تستخدم قاعدة الإنتاج للاختبارات أو لإنشاء بيانات اختبار.

## سير العمل

- الفرع الرئيسي هو `main`.
- شغّل `pnpm check` و`pnpm test` و`pnpm build` قبل كل دفع.
- لا تنشر إلى الإنتاج قبل نجاح Actions واختبارات المعاينة اليدوية وموافقة صريحة.
