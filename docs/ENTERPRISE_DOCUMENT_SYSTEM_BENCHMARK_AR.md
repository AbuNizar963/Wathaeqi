# دراسة مقارنة وتطوير وثائقي — Wathaeqi

**تاريخ المراجعة:** 24 نوفمبر 2026  
**النطاق:** مراجعة مرجعية لأنظمة إدارة الوثائق والمحتوى المؤسسي، وتحويل النتائج إلى خارطة تطوير عملية لـWathaeqi.  
**ملاحظة منهجية:** لا توجد قائمة واحدة يمكن وصفها بأنها «كل أنظمة الوثائق العالمية». لذلك اختيرت عينة ممثلة من منصات مؤسسية تجارية ومشاريع مفتوحة المصدر ووثائق معايير دولية. المقارنة مبنية على الوثائق الرسمية المنشورة، وليست اختباراً ميدانياً لكل منتج.

## 2. المعايير التي يجب أن تحكم التصميم

### ISO 15489-1:2016 — إدارة السجلات
يجب أن تكون الوثيقة الرسمية قابلة للإثبات من حيث:
- **الأصالة:** يمكن إثبات ماهيتها ومن أنشأها أو أرسلها ومتى.
- **الموثوقية:** تمثل النشاط أو المعاملة التي توثقها تمثيلاً دقيقاً.
- **السلامة:** محمية من التغيير غير المصرح به، مع إمكانية كشف العبث.
- **قابلية الاستخدام:** يمكن العثور عليها واسترجاعها وعرضها وفهمها خلال دورة حياتها.

تتطلب هذه المبادئ محتوى وبيانات وصفية وسياقاً وسياسات ومسؤوليات وضوابط، ولا تتحقق بمجرد حفظ PDF.

### PDF/A وPDF/UA
- PDF/A معيار مناسب للحفظ طويل الأجل، ولا يعني تلقائياً أن الملف مهيأ لإمكانية الوصول.
- PDF/UA يركز على بنية PDF الدلالية وإمكانية استخدامه مع التقنيات المساعدة.
- ينبغي الحفاظ على الملف الأصلي دون إعادة ترميز، وإنشاء نسخة أرشيفية مشتقة عند الحاجة، مع توثيق العلاقة والبصمة بينهما.
- لا ينبغي وصف أي ملف بأنه مطابق للمعيار قبل فحصه بأداة تحقق متخصصة.

## 3. خط الأساس المرصود في Wathaeqi

تظهر مراجعة README.md وTODO.md وملفات الواجهة والخادم والعقد المشترك أن النظام يتضمن بالفعل:
- مكتبة وثائق، وبحثاً نصياً وتصنيفات وعروض بحث محفوظة محلياً لكل مستخدم.
- رفع DOCX وPDF والصور، ومعاينة الملفات داخل النظام.
- استوديو لإنشاء الوثائق وتحرير المسودات وإصدار الوثائق وأرشفتها.
- قوالب ذات حقول ومتغيرات، ولقطات لنسخة القالب المستخدمة عند إنشاء الوثيقة.
- ترقيم رسمي وإعدادات ترويسة وشعار وعلامة مائية ورمز QR في الإعدادات/مخرجات الوثائق.
- طباعة متعددة الصفحات في ورقة A4، ومشاركة وتنزيل.
- إدارة المستخدمين والجهات وإعدادات المؤسسة، ومصادقة Appwrite وصلاحيات خادمية.
- فحوص واختبارات للمعاينة والطباعة والرفع وبعض مسارات الأمان.

### فجوات يجب التحقق منها أو استكمالها
1. البحث الكامل داخل محتوى PDF/DOCX المرفوع، بما في ذلك OCR للمستندات الممسوحة ضوئياً، غير مثبت كمسار متكامل في خط الأساس.
2. لا يظهر في نموذج الوثيقة الحالي سجل إصدارات ملف فعلي مستقل؛ توجد لقطة لنسخة القالب، وهذا ليس بديلاً عن version history للوثيقة وملفها.
3. لا توجد في نموذج الحالة الحالي إلا draft وissued وarchived؛ يلزم تقييم سير اعتماد ومهام مراجعة قبل توسيع الحالات.
4. عروض البحث المحفوظة حالياً محلية في المتصفح، ولا تتزامن بين الأجهزة.
5. يلزم فحص تصدير PDF/A وPDF/UA والتحقق الآلي من المطابقة قبل تقديم ادعاء امتثال.
6. التوقيع الإلكتروني القانوني يتطلب مزود ثقة وتدفق موافقة وأدلة تحقق؛ صورة التوقيع أو الختم وحدها ليست توقيعاً إلكترونياً موثوقاً.
7. يلزم استكمال التاريخ الهجري الاختياري، وتصدير Word، وضبط ظهور الترويسة والتذييل في المعاينة والطباعة، كما هو موضح في TODO.
8. واجهة Flutter تحتاج مطابقة فعلية مع وظائف الويب؛ وجود صفحات وثائق لا يثبت اكتمال الاتصال والمصادقة والرفع والصلاحيات.

## 4. خارطة التطوير المقترحة

### المرحلة الأولى — تجربة المكتبة والبحث
- فلاتر حسب الحالة والتصنيف والجهة ونوع الملف والفترة الزمنية.
- ترتيب حسب آخر تحديث والتاريخ والرقم والعنوان.
- بحث موحد بالعنوان والموضوع والرقم والمحتوى والبيانات الوصفية.
- عروض بحث محفوظة ومتزامنة بين أجهزة المستخدم بعد تصميم API وصلاحياتها.
- تحديد متعدد، إجراءات جماعية آمنة، وتصدير نتائج البحث.
- طرق عرض قائمة/جدول/بطاقات مع أعمدة قابلة للتخصيص، مع الحفاظ على تصميم RTL واستجابة الهاتف.

### المرحلة الثانية — دورة حياة الوثيقة
- سجل إصدارات حقيقي للملف والمحتوى والبيانات الوصفية، مع مقارنة واستعادة آمنة.
- Check-in/Check-out أو قفل تحرير متفائل حسب طبيعة المستند، مع كشف التعارضات.
- مسارات اعتماد قابلة للتهيئة: منشئ، مراجع، معتمد، مصدر، ومؤرشف.
- مهام ومسؤوليات ومهل وتنبيهات وتصعيد، مع سجل قرار واضح.
- منع تعديل النسخة الصادرة بصمت؛ أي تصحيح ينتج إصداراً جديداً موثقاً.

### المرحلة الثالثة — الالتقاط والفهرسة والذكاء
- معالجة رفع متعددة الملفات والسحب والإفلات والمسح بالكاميرا.
- OCR عربي/إنجليزي للمستندات المصورة، واستخراج النص مع مؤشر ثقة ومراجعة بشرية.
- اقتراح نوع الوثيقة والجهة والتاريخ والرقم والموضوع والوسوم، دون اعتماد آلي غير قابل للمراجعة.
- فهرسة كاملة مع تمييز مواضع النتائج في المعاينة.
- بحث دلالي/مساعد ذكاء اصطناعي اختياري، مقيد بصلاحيات المستخدم، مع إظهار مصادر الإجابة ومنع تسرب بيانات جهة إلى أخرى.

### المرحلة الرابعة — الحوكمة والأمان
- صلاحيات دقيقة على مستوى الجهة والوثيقة والعملية والحقل، تُفرض في الخادم.
- سياسات احتفاظ ومراجعة إتلاف وتعليق إتلاف قانوني عند الحاجة.
- بصمة SHA-256 للأصل والإصدارات المشتقة، وسجل أحداث غير قابل للتعديل عبر التطبيق.
- سجل تنزيل/تصدير/مشاركة/طباعة عند توافر دلالة خادمية صحيحة، مع عدم تسجيل الأسرار أو الروابط الموقعة.
- مشاركة آمنة بروابط محددة الصلاحية والنطاق، وإمكانية إبطالها.
- نسخ احتياطية واختبار استعادة وخطة تعافي، دون تنفيذ تغييرات على بيانات الإنتاج ضمن التطوير.

### المرحلة الخامسة — مخرجات رسمية وتكامل
- PDF عالي الدقة بخطوط عربية مضمّنة، مع فحص PDF/A عند طلب الأرشفة.
- دعم PDF/UA وWCAG حيثما أمكن، مع تقارير تحقق لا ادعاءات غير مختبرة.
- قوالب Word قابلة للتصدير مع اختبار RTL والجداول والخطوط.
- توقيع إلكتروني عبر مزود موثوق، وختم مؤسسي منفصل عن التوقيع الشخصي.
- QR للتحقق من صحة الوثيقة وإصدارها دون كشف بيانات غير عامة.
- API وWebhooks وتكاملات البريد والتقويم والأنظمة المؤسسية عند وجود حاجة وصلاحيات واضحة.

### المرحلة السادسة — تطبيق Flutter
- تطابق الوظائف الأساسية مع الويب: المكتبة، البحث والفلاتر، المعاينة، الاستوديو، القوالب، الاعتماد، الأرشفة، الإعدادات، والإدارة وفق الصلاحيات.
- Appwrite Bearer authentication واتصال API مطابق لـmain.
- رفع وتنزيل ملفات آمنان، وإدارة الروابط الموقعة دون تخزينها في Offline Vault.
- Offline mode للقراءة والمهام المسموح بها فقط، مع مزامنة موثوقة وتعارضات صريحة؛ لا تصدر أو تعتمد أو تحذف نهائياً دون اتصال.
- اختبارات Dart/Flutter مستقلة عن اختبارات الويب.

## 5. مبادئ التنفيذ وعدم الإضرار بالبيانات

- main هو المرجع الوظيفي للنظام الوثائقي؛ يبقى فرع Flutter مستقلاً ويُحدّث ليطابقه بتقنيات Flutter.
- لا تُنقل إجراءات برقيات قديمة إلى النظام الوثائقي لمجرد الحفاظ على أسماء API.
- لا يُجرى تغيير Appwrite schema أو permissions أو بيانات الإنتاج دون خطة ترحيل، وبيئة staging، وموافقة صريحة.
- لا يُحذف الملف الأصلي عند إنشاء OCR أو PDF/A أو نسخة معالجة؛ تحفظ العلاقات والبصمات.
- لا تضاف حالة أو صلاحية إلى الواجهة قبل فرضها في الخادم واختبارها.
- لا تُعتبر الميزة مكتملة إلا بعد اختبار الويب وFlutter وRTL والاستجابة والصلاحيات وحالات الخطأ، ومراجعة GitHub Actions.
- لا يتم الدمج أو النشر إلى الإنتاج دون موافقة المستخدم.
