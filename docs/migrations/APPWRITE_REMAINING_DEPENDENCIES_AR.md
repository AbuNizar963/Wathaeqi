> تاريخ الفحص: 19 نوفمبر 2026  
> المستودع: `AbuNizar963/Wathaeqi` فقط  
> الفرع: `migration/appwrite-functions-transfer`  
> الحالة: تدقيق قراءة فقط؛ لم تُنقل بيانات ولم تُحذف خدمة أو إعداد.

## 0. تقدم فصل التشغيل — 19 نوفمبر 2026

- أصبح `server/app.ts` يركّب واجهة المالك والمستندات فقط عبر Appwrite.
- حُذفت وحدات Supabase القديمة ومستهلكاتها ضمن نطاق الخادم القديم (مستودع البيانات، إدارة المؤسسات القديمة، مسارات البرقيات والتخزين والإشعارات، ومحدد التحقق القديم). لم تُنقل بياناتها.
- أزيل عميل Supabase الخاص بالمتصفح ومتغيرات `VITE_SUPABASE_*`، وأزيلت متغيرات Supabase الخادمية من `server/_core/env.ts` و`.env.example`.
- أزيلت خطوات Supabase CLI وقاعدة البيانات المحلية من GitHub Actions، وأزيل أمر `test:supabase`.
- أزيل `@supabase/supabase-js` من `package.json`؛ تم تحديث `pnpm-lock.yaml` آلياً بعد حذف SDK؛ ينتظر تأكيد فحوص CI والبناء.
- أضيف فحص CI يمنع عودة أي مرجع Supabase إلى مجلدات التطبيق النشطة.
- تبقى ملفات SQL القديمة تحت `supabase/` كأرشيف تاريخي فقط؛ لا يشغّلها التطبيق أو CI ولا تُحذف بيانات المشروع الخارجي.

## 2. خريطة الاعتماد التشغيلي المتبقي على Supabase

| الموضع | الاستخدام المتبقي | ما يلزم قبل الإزالة |
|---|---|---|
| `server/_core/supabase.ts` | **أزيلت** وحدة العميل الإداري بعد حذف مستهلكيها من مسار الخادم النشط | لا يوجد عميل Supabase في الشيفرة النشطة |
| `server/db.ts` | **أزيل** مستودع النظام القديم؛ استُبدل مسار المالك بمستودعات Appwrite المستقلة للوثائق والحساب والتدقيق | لا تُعاد وحدات البرقيات والإدارة القديمة ضمن نطاق المنتج الحالي |
| `server/features/organizations/organization.ts` | **أزيلت** خدمة إدارة المؤسسات القديمة؛ يستخدم API المالك `appwriteOwnerOrganizationRepository` للقراءة الضرورية فقط | لا توجد عمليات إنشاء/حذف مؤسسات في المنتج الحالي |
| `server/app.ts` | تم تحويل التطبيق إلى `ownerApiRouter` المعتمد على Appwrite؛ أزيلت منه مسارات التحقق القديمة والبرقيات والتخزين والإشعارات | لا يوجد اعتماد Supabase في مسار الخادم النشط؛ يلزم اختبار API بعد التغيير |
| `server/_core/verificationRateLimit.ts` | **أزيلت** وحدة التحديد القديمة مع مسار التحقق الخاص بالبرقيات | لا توجد خدمة تحقق قديمة مركبة في API المالك |
| `server/features/storage/storageRoutes.ts` | **أزيلت** مسارات تخزين البرقيات والشعارات القديمة؛ بقي مزود Appwrite العام فقط لاستخدام مستقبلي عند اعتماد المرفقات | لا توجد مسارات تخزين Supabase في التطبيق النشط |
| `server/_core/env.ts` و`.env.example` | **أزيلت جميع متغيرات Supabase** من إعدادات الخادم والمتصفح | إعدادات Appwrite فقط مطلوبة للتشغيل |
| `package.json` و`pnpm-lock.yaml` | أزيل أمر `test:supabase` واعتماد `@supabase/supabase-js` من `package.json`؛ تحديث `pnpm-lock.yaml` جارٍ عبر GitHub Actions | تم تحديث lockfile عبر GitHub Actions؛ يلزم تأكيد فحوص CI والبناء دون SDK |
| `supabase/migrations` و`supabase/tests` | تاريخ مخطط المصدر واختباراته | الاحتفاظ بها كمرجع ترحيل/أرشيف حتى اعتماد سياسة الأرشفة؛ لا تحذف تلقائياً |

## 3. ما هو قائم بالفعل في Appwrite

- `server/_core/appwrite.ts`: عميل خادمي، TablesDB، Storage، Tokens وUsers.
- `server/_core/appwriteAuth.ts`: مصادقة وجلسات Appwrite وملفات المستخدم.
- `server/_core/storageProvider.ts`: مزوّد تخزين Appwrite.
- `server/features/platform-settings/platformDocumentSettingsRepository.ts`: إعدادات المستندات على Appwrite.
- `server/features/organizations/organization.ts`: بعض عمليات القراءة والكتابة على Appwrite، لكنها مختلطة حالياً مع استدعاءات Supabase.

الجداول التشغيلية الأساسية في Appwrite مضبوطة حالياً مع `rowSecurity=false` وصلاحيات جدول فارغة في نتيجة الفحص. لذلك يجب أن تظل عملياتها من الخادم فقط بمفتاح إداري، مع تحقق صارم من هوية المستخدم ونطاق المؤسسة داخل كل عملية. لا يجوز كشف المفتاح أو نقل هذه العمليات مباشرة إلى المتصفح.

## 4. نقاط توقف تقنية قبل نقل API

1. `api-health` وظيفة فحص مستقلة، وليست بديلاً عن API النظام ولا تثبت عمل tRPC أو المصادقة أو الملفات.
2. مدخل Appwrite Function يستقبل كائن `req/res` الخاص بـOpen Runtimes؛ لا يجوز افتراض أنه كائن Node.js `IncomingMessage/ServerResponse` أو تمريره مباشرة إلى Express و`serverless-http`.
3. يلزم اختبار cookies وheaders وquery وJSON وCORS وطرق HTTP وأكواد الاستجابة، إضافة إلى تنزيل الملفات الثنائية والتصدير PDF ورفع الملفات.
4. التطبيق يضم مسارات بأجسام طلب كبيرة (استيراد Excel/صفوف ورفع مرفقات). يجب ألا تمر الملفات الكبيرة عبر وسيط Function قبل اعتماد رفع مباشر إلى Appwrite Storage مع تفويض خادمي.
5. يلزم تصميم بديل للـRPCs والقيود الذرية في تخصيص الأرقام، انتقال حالة البرقية، الحذف الآمن، حدود المعدل، والعمليات المركبة. عمليات القراءة ثم الكتابة المنفصلة لا تكافئ معاملة ذرية.
6. يجب مطابقة كل جدول وعمود وفهرس وعلاقة وقيم enum وحدود nullable/default قبل ترحيل البيانات.

## 5. تدقيق تناقض التوثيق والنشر

أظهر فحص شجرة الفرع الحالية وجود `netlify.toml` و`netlify/functions/api.mts` و`netlify/functions/api-health.mts`. لذلك فإن الوصف الأقدم في تقرير التدقيق الذي ذكر عدم وجود catch-all أو ملف إعداد Netlify لم يعد مطابقاً لشجرة الفرع الحالية، ويجب عدم الاعتماد عليه لوصف النشر الراهن.

لا تُحذف ملفات Netlify أو إعداداتها حتى يعمل بديل API على Appwrite وتنجح اختبارات القبول الكاملة. كما لا يُعد نجاح Site الواجهة أو Health Function اختباراً لعمل API.

## 6. ترتيب التنفيذ الملزم

1. إكمال جرد جميع استدعاءات Supabase وRPCs والاعتماد على روابط التخزين القديمة.
2. مطابقة مخطط المصدر والهدف واختبارات صلاحيات Appwrite، دون تعديل بيانات الإنتاج.
3. بناء بديل خادمي ذري للعمليات الحرجة، ثم نقل نطاق واحد في كل مرة مع اختبارات وحدات وتكامل.
4. إعداد خطة ترحيل بيانات قابلة لإعادة التشغيل والتحقق، مع نسخة احتياطية قابلة للاستعادة ومقارنة أعداد السجلات والعلاقات والبصمات.
5. نقل المصادقة والجلسات والملفات والرفع/التصدير، ثم اختبار الويب كاملاً.
6. نقل API إلى Appwrite Functions بتوافق موثق ومختبر، وربط الواجهة بالعنوان الصحيح.
7. تشغيل GitHub Actions واختبارات القبول والنشر التجريبي ومراجعة السجلات.
8. بعد تحقق جميع الشروط وموافقة المالك، إزالة Netlify وSupabase من التشغيل والاعتمادات. الاحتفاظ بملفات SQL الأرشيفية لا يعني استمرار الاعتماد التشغيلي.

## 7. حدود هذا السجل

هذا المستند يوثق حالة الفحص ولا ينفذ ترحيل بيانات، ولا يغير صلاحيات Appwrite، ولا يبدل مسارات التشغيل، ولا يحذف Netlify أو Supabase. جميع بيانات Supabase الأصلية تبقى كما هي حتى تنفيذ ترحيل مستقل موثق ومتحقق منه.
