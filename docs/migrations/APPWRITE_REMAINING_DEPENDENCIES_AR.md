# حالة اعتماد وثائقي على Appwrite

**آخر تحديث:** 19 نوفمبر 2026  
**الفرع:** `migration/appwrite-functions-transfer`

## النتيجة

أصبحت مسارات التشغيل الحالية في هذا الفرع مبنية على Appwrite:

- المصادقة والجلسات: Appwrite Auth مع جلسة خادمية موقعة.
- ملفات المالك والوثائق والقوالب وإعدادات المؤسسة: Appwrite TablesDB.
- الملفات: Appwrite Storage عبر `AppwriteStorageProvider`.
- واجهة API: Appwrite Function `wathaeqi-api`.
- الواجهة: عميل tRPC مخصص للـOwner API ويستخدم `VITE_APPWRITE_API_URL`.

أزيلت وحدات قاعدة البيانات القديمة من الخادم النشط، ومتغيرات البيئة القديمة، واعتماد SDK القديم، وملفات SQL/ORM التاريخية من شجرة المستودع. لا توجد حاجة إلى تهيئة خدمة قاعدة بيانات بديلة خارج Appwrite لتشغيل مسارات المالك الحالية.

## ما لم يحدث

- لم تُنسخ بيانات قديمة إلى Appwrite.
- لم تُحذف أو تُعدّل بيانات أي مشروع خارجي.
- لم يتغير حساب المالك الحالي أو كلمة مروره نتيجة تنظيف المستودع.
- لم يتم دمج فرع الترحيل إلى `main` أو نشره على موقع الإنتاج.

## نقاط التحقق المتبقية قبل الدمج

1. نجاح GitHub Actions على آخر commit بعد تنظيف الملفات.
2. نجاح بناء Appwrite Function وموقع المعاينة من نفس commit.
3. اختبار تسجيل الدخول واسترداد إعداد المالك وتغيير كلمة المرور من المتصفح.
4. اختبار إنشاء وثيقة وحفظها وإصدارها وأرشفتها، مع التأكد من بقاء البيانات مقيدة بمالكها.
5. اختبار الرفع والتنزيل إذا كانت واجهة المرفقات مفعلة في نطاق الإصدار.
6. مراجعة حماية معدل محاولات الدخول عند تعدد نسخ الخدمة؛ الحارس الإضافي الحالي داخل ذاكرة العملية، بينما يظل Appwrite Auth مسؤولاً عن حماية المصادقة الأساسية.

لا يُعد نجاح البناء وحده إثباتاً لاكتمال اختبار المستخدم النهائي.
