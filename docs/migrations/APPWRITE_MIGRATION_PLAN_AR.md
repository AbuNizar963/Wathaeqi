# خطة ترحيل Wathaeqi من Supabase إلى Appwrite

> الحالة: مرحلة الجرد والتصميم فقط — لا يوجد ترحيل بيانات أو تحويل تشغيل حتى الآن.
> النطاق: فرع الويب والخادم في هذا المستودع، `AbuNizar963/Wathaeqi` فقط.

## 1. القرار المعماري

- Appwrite هو الهدف النهائي للمصادقة والبيانات والملفات.
- يبقى Supabase المصدر التشغيلي الحالي إلى أن تكتمل المراحل والاختبارات ويوافق مالك النظام على التحويل.
- يمنع وضع Appwrite API key في كود المتصفح أو متغيرات `VITE_*`. العمليات المميّزة تبقى على الخادم فقط.
- لا تُمنح صلاحيات عامة للجداول الحساسة. تُفرض صلاحيات المؤسسة والمستخدم على الخادم، مع اختبارات منع الوصول بين المؤسسات.
- لا تُحذف بيانات أو مخططات أو مفاتيح Supabase خلال مراحل البناء والتحقق.

## 2. جرد مخطط المصدر

يحتوي مخطط Drizzle الحالي على 14 جدولاً:

| جدول المصدر | الغرض | هدف Appwrite الموجود |
|---|---|---|
| organizations | شجرة المؤسسات والجهات | organizations |
| users | ملف المستخدم وربطه بهوية المصادقة | users + Appwrite Auth identity |
| department_settings | إعدادات كل مؤسسة والترقيم | department_settings |
| platform_document_settings | إعدادات العلامة المائية والتحقق | platform_document_settings |
| organization_memberships | عضويات المستخدم وأدواره | organization_memberships |
| telegrams | أصل البرقية وحالتها وأرقامها | telegrams |
| telegram_versions | سجل نسخ البرقية | telegram_versions |
| telegram_attachments | بيانات وصفية للمرفقات ومفاتيح التخزين | telegram_attachments + Storage bucket |
| telegram_actions | أحداث وإجراءات البرقية | telegram_actions |
| telegram_routes | الإحالات والاستلام والموافقات | telegram_routes |
| notifications | إشعارات المستخدمين | notifications |
| push_subscriptions | اشتراكات Web Push | push_subscriptions |
| mobile_push_tokens | رموز إشعارات الهاتف | mobile_push_tokens |
| audit_logs | سجل التدقيق وسلسلة التجزئة | audit_logs |

المخطط يحتوي أيضاً على 9 أنواع enum. فحص Appwrite الحالي أظهر أعمدة بصيغة enum وقوائم عناصر لهذه القيم في الجداول المقابلة؛ يجب مطابقة عناصرها مع المصدر آلياً، والإبقاء على تحقق الخادم واختبارات رفض القيم غير المسموحة:
`user_role`, `telegram_classification`, `telegram_priority`, `telegram_category`, `telegram_status`, `number_system`, `organization_type`, `organization_member_role`, `telegram_route_status`.

يوجد إجراء PostgreSQL باسم `public.allocate_serial_number`. يجب استبداله بعملية خادمية آمنة تمنع تكرار الأرقام تحت الضغط، لا بمجرد قراءة العداد ثم زيادته من العميل.

## 3. جرد هدف Appwrite الحالي

قاعدة البيانات: `wathaeqi-db`
مخزن الملفات: `document-attachments`

الجداول الموجودة التي تطابق مخطط المصدر بأسمائها:
`organizations`, `users`, `department_settings`, `platform_document_settings`, `organization_memberships`, `telegrams`, `telegram_versions`, `telegram_attachments`, `telegram_actions`, `telegram_routes`, `notifications`, `push_subscriptions`, `mobile_push_tokens`, `audit_logs`.

وتوجد جداول أخرى في Appwrite لا تقابل جدولاً في مخطط Drizzle الحالي:
`documents`, `templates`, `contacts`, `attachments`, `app_records`.
يجب تحديد مالكها واستخدامها قبل أي تعديل؛ لن تُحذف أو يعاد توظيفها ضمن هذا الترحيل دون إثبات الحاجة وموافقة منفصلة.

### فروق وتدقيقات مطلوبة

1. ظهر أن `rowSecurity` مفعّل في أربعة جداول من أصل الجداول التي فُحصت، بينما جداول الأعمال الأساسية مثل `telegrams`, `users`, `organizations`, `telegram_routes` و`audit_logs` لا تعتمد حالياً على row-level security في Appwrite. هذا لا يثبت انكشافها للعامة؛ لكنه يستلزم تدقيق صلاحيات الجدول والصف والـ API قبل ربط التطبيق.
2. صلاحيات الجداول الأساسية الظاهرة في إعداد Appwrite فارغة. يجب اختبار السلوك الفعلي وعدم افتراض أن غياب الصلاحيات يعني سياسة آمنة أو مناسبة.
3. مخطط Appwrite لـ `users` لا يحتوي `passwordHash` الذي يظهر في مخطط المصدر. لا ننقل تجزئات كلمات المرور أو نعيد استخدامها دون تصميم ترحيل موثوق. يجب تقرير مسار إعادة تعيين/تفعيل الحسابات واختباره.
4. توجد علاقات Appwrite إضافية مثل `organization`, `creator`, `updatedBy`؛ يجب التأكد من توافقها مع مفاتيح المصدر وسياسة الحذف قبل استخدامها.
5. يجب مطابقة كل عمود، نوع، طول، nullable/default، unique index، index، علاقة، وسلوك حذف قبل كتابة أي importer.

## 4. حدود المصادقة والجلسات

المصدر الحالي ينشئ جلسات موقعة في الخادم عبر cookie باسم `police_telegrams_session`، ويتحقق من `sessionVersion`، ويحتوي منطق كلمات مرور محلياً. هذا ليس مجرد تبديل SDK.

التصميم المستهدف:
- استخدام Appwrite Auth لإثبات هوية المستخدم.
- الاحتفاظ بملف المستخدم وعضوياته وأدواره في قاعدة البيانات مع ربط موثوق بمعرّف Appwrite Auth.
- إصدار/تجديد جلسة HTTP آمنة من الخادم مع `HttpOnly`, `Secure` في الإنتاج، و`SameSite` مناسب، وحماية CSRF حيث يلزم.
- عدم الثقة في الدور أو المؤسسة القادمَين من العميل أو بيانات الملف الشخصي القابلة للتعديل.
- خطة واضحة للحسابات الحالية وكلمات المرور والاسترداد وتدوير الجلسات قبل تفعيل Appwrite Auth.

## 5. طبقة البيانات والعمليات الذرية

- إنشاء مستودعات server-side لكل نطاق (المستخدمون، المؤسسات، البرقيات، المسارات، الإعدادات، الإشعارات، التدقيق).
- الحفاظ على حدود المؤسسة في كل استعلام قراءة وكتابة وتنزيل وتصدير وحذف.
- تصميم عملية آمنة لتخصيص الأرقام التسلسلية ومعالجة idempotency وتعارض الطلبات؛ يجب اختبار التزامن.
- الحفاظ على ترتيب الإحالات والموافقات وسجل الإجراءات والإصدارات.
- تقييم كل RPC/trigger/constraint في Supabase قبل نقل السلوك. لا يكفي نقل أسماء الجداول.
- جعل عمليات الترحيل قابلة لإعادة التشغيل مع سجل checkpoints ونتائج تحقق، دون تعديل المصدر.

## 6. الملفات والمرفقات

- نقل الملفات إلى bucket خاص، مع مفاتيح غير قابلة للتخمين ومقيدة بالمؤسسة.
- التحقق من المستخدم والمؤسسة والبرقية عند بدء الرفع وعند إنهائه وعند التنزيل.
- التحقق من الحجم والنوع وSHA-256 وبيانات الملف، والحفاظ على حالة الفحص.
- عدم إظهار روابط دائمة أو مفاتيح API أو روابط موقعة في السجلات.
- لا يُحذف أي ملف من Supabase حتى تتم مقارنة العدد والحجم والبصمات وتجربة التنزيل من Appwrite.
