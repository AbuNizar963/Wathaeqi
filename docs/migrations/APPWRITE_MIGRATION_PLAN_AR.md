# خطة وحالة اعتماد Appwrite في وثائقي

**آخر تحديث:** 19 نوفمبر 2026  
**فرع العمل:** `migration/appwrite-functions-transfer`

## الهدف

تشغيل مساحة عمل المالك والوثائق باستخدام Appwrite Auth وTablesDB وStorage وFunctions، مع عدم نقل أو تعديل البيانات التاريخية خارج هذا النطاق.

## التنفيذ الحالي

- Appwrite Auth هو مصدر التحقق من كلمة مرور المالك والجلسة.
- Appwrite TablesDB يخزن ملف المالك وسياق المؤسسة والوثائق والقوالب وإعدادات الوثائق وسجلات الإعداد.
- Appwrite Function `wathaeqi-api` تستضيف واجهة API الخاصة بالمالك.
- Appwrite Storage هو موفر الملفات في طبقة `server/_core/storageProvider.ts`.
- عميل الواجهة يستخدم `ownerTrpc` ويرسل الطلبات إلى عنوان Appwrite Function.
- لا توجد تبعيات تشغيلية على خدمة قاعدة بيانات أو مصادقة خارج Appwrite في مسار المالك الحالي.
- أزيلت أدوات ORM القديمة ومخططات SQL القديمة من المستودع؛ لا يؤدي ذلك إلى حذف أو تغيير بيانات أي مشروع خارجي.

## حماية البيانات والحساب

- يُحتفظ بحساب المالك الحالي ولا يُنشأ حساب مكرر.
- لا تُنقل كلمات مرور أو تجزئات قديمة إلى Appwrite Auth.
- إعداد كلمة المرور الأولي يتم عبر مسار المالك لمرة واحدة ورمز سري مستقل.
- لا تُرسل الأسرار أو كلمات المرور في المحادثات أو السجلات.
- لا يتم إجراء أي كتابة اختبارية على قاعدة Appwrite الحية.

## الاختبارات المطلوبة

- TypeScript وPrettier وVitest والبناء.
- التحقق من تضمين Appwrite API في حزمة Function وعدم وجود SDK قديم.
- CORS وطلبات tRPC من نطاق المعاينة الفعلي.
- تسجيل الدخول، جلسة المتصفح، إعداد كلمة المرور، تغييرها وتسجيل الخروج.
- CRUD للوثائق والقوالب، الإصدار والأرشفة، وتعارض التحديث.
- التحقق من ملكية الصفوف والملفات ومنع الوصول غير المصرح.

## النشر

المعاينة المعزولة فقط هي وجهة التحقق في هذه المرحلة. لا تعديل لموقع الإنتاج ولا دمج إلى `main` دون موافقة صريحة بعد نجاح الاختبارات والتحقق اليدوي.
