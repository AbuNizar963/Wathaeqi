# تطبيق وثائقي للهاتف

تطبيق Flutter هو عميل الهاتف لنظام وثائقي، ويتصل مباشرة بواجهة Appwrite Function المنشورة. هذا الفرع مستقل للتطبيق ولا يحتوي نسخة خادم أو قاعدة بيانات بديلة؛ تبقى المصادقة والصلاحيات ونطاق الجهة مسؤولية Appwrite API.

## المتطلبات والتشغيل

- Flutter 3.47.2 وDart الموافق له، كما يحدده GitHub Actions.
- Android Studio أو Xcode بحسب المنصة، ومحاكي أو جهاز اختبار.

من جذر المستودع:

```bash
cd mobile
flutter pub get
flutter run
```

عنوان Appwrite Function الافتراضي مضبوط في `mobile/lib/api.dart`:

`https://wathaeqi-api.fra.appwrite.run`

لتغييره أثناء التطوير:

```bash
flutter run --dart-define=API_BASE_URL=https://your-server.example
```

وعند الاتصال بخادم محلي من محاكي Android:

```bash
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:3000
```

لا تضع أسرار الخادم أو المفاتيح الإدارية في التطبيق. لا ترفع ملفات Firebase المحلية الحساسة؛ راجع `FIREBASE_SETUP_AR.md` لإعداد الإشعارات.

## علاقة التطبيق بـ Appwrite

- يستخدم الويب والهاتف حسابات المستخدمين والجهات والبرقيات والصلاحيات نفسها.
- تُراجع عقود API المنشورة في Appwrite عند تغيير إجراءات المستخدم أو الوثيقة أو الجهة؛ لا تُنسخ ملفات خادم إلى هذا الفرع.
- لا تعتمد على إخفاء زر أو `mobile_access_policy.dart` لحماية عملية؛ يجب أن يفرض الخادم التفويض ونطاق الجهة في كل طلب.
- تغييرات قاعدة البيانات إضافية ومتوافقة: أضف ترحيلًا جديدًا، ولا تعدّل ترحيلًا مطبقًا، واختبر النسخة القديمة والجديدة من التطبيق في بيئة محلية أو staging قبل النشر.
- التخزين المحلي للقراءات أو صندوق الصادر لا يثبت نجاح الكتابة على الخادم ولا يتجاوز التحقق منه. عند تغير المستخدم أو انتهاء الجلسة، لا تعرض cache حساب آخر.

## تنظيم شيفرة Flutter

يبقى `lib/main.dart` نقطة الدخول المستقرة. نُقلت وحدة مستند البرقية إلى `lib/features/telegrams/documents/official_telegram_document.dart`، واختبارها إلى `test/features/telegrams/documents/`. تُنقل بقية الملفات المسطحة تدريجيًا حسب الميزة، مع تحديث imports وتشغيل التنسيق والتحليل والاختبارات والبناء في كل خطوة. خريطة ملكية المستودع كاملة في [`docs/architecture/REPOSITORY_STRUCTURE_AR.md`](../docs/architecture/REPOSITORY_STRUCTURE_AR.md).

## التنسيق والاختبارات

من مجلد `mobile`:

```bash
./tool/format_dart.sh --check
flutter analyze
flutter test --concurrency=1 --reporter expanded
flutter build apk --debug
```

لإصلاح تنسيق Dart قبل المراجعة:

```bash
./tool/format_dart.sh --fix
```

تُشغّل GitHub Actions فحوص Flutter عند تغييرات `mobile/` على `flutter-mobile-app`. يعتمد التطبيق على Appwrite Function المنشورة، ولا يحتوي هذا الفرع على نسخة خادم أو قاعدة بيانات بديلة. لا تستخدم formatter لإخفاء تغيير سلوكي أو ضغط الملفات في سطر واحد.

## إصدار Android

لا يُنشر إصدار جديد تلقائيًا مع كل دمج. لبناء APK موقّع ونشره، شغّل يدويًا سير `.github/workflows/flutter-mobile.yml` واختر `flutter-mobile-app` كفرع التشغيل. يوجد تعريف سير `workflow_dispatch` أيضًا على `main` كي يظهر في GitHub Actions، لكن وظيفة البناء والإصدار مقيدة بفرع التطبيق. يلزم اعتماد التغيير وتوفر أسرار توقيع Android وإعداد Firebase. يتحقق السير من توقيع الحزمة وبصمتها وSHA-256، ولا يرسل إشعارًا للأجهزة إلا إذا كانت جاهزية خادم الإشعارات معدّة. لا يؤدي طلب الدمج وحده إلى إصدار عام.

## الإشعارات والعمل دون اتصال

- يمكن أن تعرض الشاشات الأساسية بيانات قرأها التطبيق سابقًا عند انقطاع الشبكة.
- الكتابات والإحالات وتغييرات الحالة لا تعتبر ناجحة حتى يؤكدها الخادم؛ تعرض حالات الفشل أو التعارض للمراجعة.
- لا تُعطل قيود نوع المرفق أو حجمه أو التحقق من الجهة.
- اختبر تسجيل الدخول والخروج وانتهاء الجلسة وتبديل الحساب قبل اعتماد أي تعديل على التخزين المحلي أو المزامنة.
